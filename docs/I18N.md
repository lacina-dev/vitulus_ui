# How to translate the robot UI (en / cs)

The UI speaks **English** (source + fallback) and **Czech**. The owner switches it in
**Settings › App › Language**; the choice is stored on the robot and every device follows it.
Default: English. No build step — dictionaries are plain JS files, the help is Markdown.

## Where things are

| What | Where |
|---|---|
| dictionaries | `nodes/templates/assets/js/i18n/en.js` (source), `i18n/cs.js` |
| runtime | `nodes/templates/assets/js/vt_i18n.js` (`window.VTI18n`), loaded right after `vt_mock.js`, before every module |
| the App tab | `nodes/templates/assets/js/vt_app_settings.js` (`window.VTAppSettings`) |
| stored choice | robot: `~/.vitulus/ui/ui_settings.json` via `GET/POST /api/ui_settings` (webnode); copy in localStorage `vitulus_lang` |
| help | `docs/help/<id>.md` (English) + `docs/help/cs/<id>.md` (Czech) |
| check | `node tools/test_i18n.node.js` (`--missing` lists missing keys) |

## Keys

`area.thing[.detail]`, lower case, dots: `settings.tab.app`, `app.lang.title`, `help.search`.
The dictionaries are split into blocks per module (`/* ---- @frag map_view: … */` …
`/* ---- @end map_view */`), the same blocks in `en.js` and `cs.js`; a new key goes into the block of
its module. `common.*` (Save, Cancel, ON/OFF, Loading…) is shared by every module — reuse it
instead of a new key for the same word. One key per text; the same word in two places with two meanings gets two keys. The area is the
panel or module (`map`, `program`, `settings`, `agent`, `support`, `needs`, `log`, `status`…).
Every key goes **first into `en.js`**, then into `cs.js`. A key missing in `cs.js` shows the
English text; a key missing in `en.js` shows the key itself (and the test fails).

- Placeholders: `'Nothing found for “{q}”.'` → `t('help.nothing', {q: raw})`. A translation must
  keep the same `{names}` (the test checks).
- Plurals: `key.one`, `key.other` in English; Czech adds `key.few` (2–4) and `key.many`
  (decimals): `VTI18n.tn('agent.jobs', n)` picks the form by `Intl.PluralRules`.
- Do not build sentences from pieces (`'Saved ' + n + ' items'`) — word order differs; use one
  key with placeholders.
- Language names are never translated (`English`, `Čeština`).
- Czech style: tykání (as in the chat), short, the same terms as the help. Robot words that are
  printed on buttons the robot itself reports (`DOCKED`, `RTK FIX`, ROS topic names) stay as
  they are.

RTAB-Map, rosbag, UTM, Wi-Fi, FPS, units (m, cm, V, A, Nm, °). Robot state words the robot

Style: tykání, short and natural (not word for word); buttons use the infinitive as in Czech
software (**Uložit**, **Zrušit**), hints are sentences. Czech is usually ~20 %
longer — on a phone prefer a shorter word over a wrapped button.

## Static text in `index.html`

```html
<a ... href="#tab_app" data-i18n="settings.tab.app">App</a>             <!-- textContent -->
<input data-i18n-placeholder="log.search" placeholder="Search text…">
<button data-i18n-title="log.pause" data-i18n-aria-label="log.pause" title="Pause autoscroll">
```

Keep the English text in the markup (first paint, search in the HTML). `data-i18n` replaces the
**whole** text of the element — an icon inside would be lost, so wrap only the words:
`<button>ON&nbsp;<i class="la la-check"></i></button>` → `<button><span data-i18n="common.on">ON</span>&nbsp;<i …></i></button>`.
Do not put `{{ … }}` into index.html — it is a Jinja template.

## Text made by JavaScript

```js
var t = function (k, v) { return window.VTI18n ? VTI18n.t(k, v) : k; };
el.textContent = t('needs.title');
VTI18n.tag(button, 'agent.stop');               // sets data-i18n + translates — follows every switch
VTI18n.tag(input, 'agent.input', 'placeholder');
VTI18n.onChange(function (lang) { render(); }); // or re-render what you drew with t()
```

The switch is **live** (no reload): `VTI18n.apply(document)` re-translates every `data-i18n*`
element, then `onChange` subscribers and the `vt:lang` document event run. So either tag an
element (`VTI18n.tag`) or re-render on `onChange`. Text that is only drawn once at start and
neither tagged nor re-rendered keeps the old language until a reload — that is the one thing to
avoid when translating a module.

Values coming from the robot or the agent (ROS states, log lines, agent messages, names of maps
and programs) are data, not UI text: never translate them.

## Help (`docs/help/`)

- English topic `docs/help/<id>.md` is the source. A Czech topic is `docs/help/cs/<id>.md` with
  the **same `id`, `group` (English group name — it is a key), `order`, `icon`, `related`** and
  the same `ui:` keys; `title`, `summary`, `keywords` and the text are Czech.
- Anchors are slugs of the Czech headings (`## Napájení` → `#napájení`), so the `ui:` anchors
  and links to a translated topic use Czech anchors; links to a topic not translated yet use its
  English anchors. When you translate a topic, fix links pointing to it (the test tells you).
- Images: `../img/x.svg` (or `img/x.svg`), robot icons `../../../nodes/templates/assets/img/…`.
- Server: `GET /help/docs.json?lang=cs` returns the English `docs` plus `translations`; the pane
  (`vt_help.js`, `VTHelpMd.merge`) shows the Czech topic where it exists and the English one with
  a note *not translated yet* elsewhere. Markdown is read live (no restart).
- Every change of the UI still updates the help — in English **and** in Czech for translated
  topics (`docs/help/README.md`).

## Checklist

1. New text → key in `en.js` + `cs.js`, `data-i18n` / `VTI18n.t` / `VTI18n.tag` at the place.
2. `node tools/test_i18n.node.js` — fails on keys missing in `en.js`, placeholders, broken Czech
   help; reports what is not translated yet. Also `node tools/test_help_docs.node.js`.
3. Deploy: `tools/restart_webnode` (JS / HTML changed), open the UI on a PC and a phone
   (`?mock`), switch the language in Settings › App both ways.

## Adding a language

Add `{code, name}` to `LANGS` in `vt_i18n.js`, the code to `UI_LANGS` in `nodes/webnode`, a
dictionary `i18n/<code>.js` + its `<script>` in index.html, `LANGS` in `tools/test_i18n.node.js`,
and `docs/help/<code>/`.
